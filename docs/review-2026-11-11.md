# Review: Axiomatic Design in HCL

Date: 2026-11-11

Scope: the current working-tree specification and examples, including the adopted attachment RFC.

Method: the requested `axiomatic-software-design` skill and its source notes; scholarly research through SciSpace; official HCL documentation.

## Assessment

The proposed language is a sound direction for recording and reviewing Axiomatic Design (AD). Keep native HCL, explicit FR–DP influences, unknown-by-default cells, qualified conclusions, and separately owned attachments. The main work before implementing the Go analyzer is to make the normative semantics complete and reproducible.

The largest risk is that two reasonable implementations could accept different models or derive different conclusions from the same files. This is a specification review, not evidence that a future implementation satisfies its contracts. The absence of the planned Go tool is expected, not a defect.

This review uses the working files, including existing uncommitted changes. ## 1. What is Axiomatic Design?

Axiomatic Design, developed by Nam P. Suh, separates what a system must achieve from how its design achieves it. It maps customer needs to functional requirements (FRs), FRs to design parameters (DPs), and DPs to process variables (PVs) that realize the design. Decomposition zigzags between requirements and selected solutions. Kim, Suh, and Kim apply the method to software and module integration. [S1, S2]

Its two axioms guide selection:

1. **Independence Axiom:** maintain independence of FRs. With FR rows and DP columns, a diagonal influence matrix is uncoupled; a triangular mapping is decoupled when the necessary design sequence is respected. A coupled mapping requires revisiting interacting choices.
2. **Information Axiom:** among feasible designs satisfying independence, prefer the lowest information content, `I = -log2(p)`, where `p` is the probability of meeting the required acceptance ranges. For a complete design, use joint success probability; summing marginal information requires a justified probability model. [S3]

For this review, an influence means that varying a DP materially affects an FR under stated conditions. A software dependency or runtime call alone does not establish an influence. Unknown effects cannot establish independence. These evidence safeguards follow the supplied skill.

The skill deliberately adapts the historical paper: it treats architectural mechanisms and policies as DPs, whereas the paper often uses input data as DPs and routines as PVs. The existing rationale correctly explains that adaptation. Neither the method nor an asserted matrix proves software correctness.

## 2. What is HCL?

HCL means **HashiCorp Configuration Language**. It provides attributes, labeled blocks, expressions, and parsing/decoding APIs for application-defined configuration languages. The application supplies its vocabulary and semantics. HCL has native and JSON syntaxes; an application chooses what it supports. [H1, H2]

RequirementsHCL is therefore a domain language built on HCL. HCL supplies the syntax; this repository must define what `fr`, `dp`, `influence`, and their references mean. Terraform is another language built using HCL, not the meaning of every HCL file.

Using native HCL and the Go `github.com/hashicorp/hcl/v2` packages is appropriate. Restricting expressions to literal data and static references is also reasonable. The native parser accepts more expressions than this profile permits, so syntax admission and domain validation must remain separate. [H3, H4]

## 3. What the proposal already gets right

- Needs, constraints, FRs, DPs, PVs, and modules have distinct roles. Child FRs arise under selected parent DPs rather than from an isolated requirements tree.
- `controls` records a proposed pairing rather than proving a material diagonal. Missing influences remain unknown, including cross-branch effects.
- Exact leaf facts survive aggregate parent claims; refinement obligations remain visible. Local sibling independence does not establish whole-system independence.
- Conditional, source, and supported conclusions are distinguished. The examples retain missing criteria, unvalidated premises, and the robot transcription caveat.
- Design/configuration order is distinguished from runtime flow. S/C/F junctions do not imply automatic concurrency, a central orchestrator, or a safe feedback algorithm.
- Evidence identifies joint success, candidate revision, context, workload, and horizon. Zero observed failures do not establish certainty.
- Attachments have typed subjects and separate owners. Binding matches and resolved behavior links do not prove FR satisfaction. The RFC appropriately limits its independence claim to a fixed-contract subtree.

Preserve these choices. Several recommendations below complete their contracts rather than replace the design.

## 4. Recommended improvements

Priority **P1** means resolve before relying on Go analysis results; **P2** means resolve before treating the language and its interoperability contracts as stable. Locations refer to the reviewed files.

### R1 — P1: Publish a complete normative field schema

**Location:** `docs/language.md:422–473`, `515–619`; examples throughout.

The reference lists many fields but does not consistently specify types, cardinality, requiredness, defaults, permitted target kinds, or nullability. This matters because unknown fields are errors. For example:

- Library FRs use a scalar `need`; the self-design uses a list. The accepted union and its normalization are not defined.
- `scenario.kind`, `expect.under`, and decision-level `context`, `workload`, and `horizon` appear in examples without complete field contracts in their respective descriptions.
- Common metadata such as `cites`, `origin`, and `alias` lacks a complete applicability table. `source` and `cites` on influences need distinct meanings.
- `ranges`, `criterion.value`, `flow.steps`, and the permitted enums for several `kind`/`role` fields lack complete types.
- The literal profile permits `null` only where allowed, but core fields do not have a complete nullability specification.

**Recommendation:** add one authoritative schema appendix covering every block and nested block. Define a reference-target table and distinguish absent, empty, and null values. Define the snake_case label grammar and nested namespaces. Keep readable summaries linked to this source of truth.

**Acceptance:** every nonhistorical example can be checked against the schema without inferring types from example usage. Add negative fixtures for wrong kinds, unknown fields, nulls, duplicates, and invalid cardinalities.

### R2 — P1: Specify candidate activation and hierarchy closure

**Location:** `docs/language.md:445–473`, `533–536`.

Explicit candidates select DPs, but the rules for the rest of a snapshot are incomplete. A rejected parent DP can have child FRs and selected child DPs. Decisions can cover different scopes. It is unclear whether a candidate's DP list is a complete design or a replacement for the addressed branch, and how multiple decisions compose.

**Recommendation:** define candidate scope, inheritance of decision metadata, activation of common DPs, parent closure, and treatment of inactive branches. Require every active child to have an active ancestry and retain inactive records without treating them as default-design coverage failures. Define which influences, modules, PVs, evidence, and attachments apply to a snapshot. Diagnose incompatible decision combinations instead of choosing by file order.

If the first version supports only one explicitly selected candidate for the whole model, say so. A deliberately narrow rule is preferable to implicit composition.

**Acceptance:** switching between two mechanisms for one FR activates the correct child hierarchy and never incorporates the unselected alternative's effects. Test nested alternatives, overlapping decisions, and a candidate omitting a required ancestor.

### R3 — P1: Define applicability and cell resolution as an algorithm

**Location:** `docs/language.md:475–513`.

The reference requires preserving relations, detecting overlapping contradictions, and leaving missing cells unknown, but does not fully define the operation. `under` accepts a context or workload; there is no complete rule for omitted selection, context/workload matching, context overlap, or one-sided `excludes`. `holds_if` and default cells add more qualifications.

**Recommendation:** specify a resolution table covering applicability, premise status, exact facts, defaults, duplicate compatible facts, explicit unknowns, and conflicts. Define whether a validated exact fact can coexist with a weaker unknown assertion, and whether an exact fact overrides a contradictory `cells` default or diagnoses it. Define how a DP-level premise qualifies its proposed control and related conclusions.

State whether `from = [dp.a, dp.b]` expands into two independent influence assertions. The self-design appears to use it that way, but a collective effect of changing both DPs together is a different claim. Either exclude interaction-only claims explicitly or model them separately; do not silently turn them into individual effects.

**Acceptance:** permuting facts and files leaves the same resolved cells and provenance. Test unconditional plus conditional records, overlapping contexts, excluded contexts, an invalidated zero premise, and an exact relation competing with a default.

### R4 — P1: Make pairing, classification, and sequencing reproducible

**Location:** `docs/language.md:24–41`, `465–473`, `517–525`.

The conceptual classification is good, including the fact that a known cycle can establish coupling despite other unknowns. The missing detail is how to choose a meaningful pairing when several DPs control several FRs, and what result to return when no unique pairing exists. Rectangular mappings also need a specified result beyond requiring a separate assessment.

**Recommendation:** derive a pairing only when the authored control relation determines it unambiguously; otherwise report ambiguity or require an explicit pairing assertion. Do not rematch controls merely to improve classification. Preserve labels when reordering paired rows and columns together. Require effective diagonals before square classification, and specify uncontrolled and redundant-control findings separately from unresolved evidence.

For an established pairing, define a precedence edge `DPj → DPi` when `DPj` materially affects `FRi` off the diagonal. Topological order gives a lower-triangular design sequence; a directed material cycle prevents it. Unknown edges do not become absent edges. Distinguish supported versus conditional diagonals and cycles before emitting qualified results.

For example:

| Outcome / control | DP1 | DP2 |
|---|---|---|
| FR1 | X | 0 |
| FR2 | X | X |

This requires DP1 then DP2: establish FR1 through DP1, then adjust DP2 for FR2 without changing FR1. A later DP1 change requires reconsidering FR2. This is design sequencing; runtime order needs separate contracts.

**Acceptance:** test diagonal, triangular, permuted triangular, material cycle with unrelated unknowns, unknown diagonal, uncontrolled FR, ambiguous pairing, and both rectangular orientations. Test alternative valid topological orders.

### R5 — P1: Define hierarchical composition and impact limits

**Location:** `docs/language.md:460–463`, `504–513`, `598–601`.

The proposal correctly rejects automatic parent-to-leaf propagation. It still needs an operational definition of a compositional argument and of a contradiction between a parent claim and an exact descendant effect. Different parent and child criteria can make a leaf influence compatible with an aggregate zero; ancestry alone does not prove contradiction.

`allocated_from` records a link but not how child outcomes jointly imply the parent criterion. The effect of multiple controls on decomposition and master-matrix membership also needs an explicit rule.

**Recommendation:** define where outcome arguments live, their criterion scope, and the qualification of unverified arguments. Treat an apparent ancestor/descendant disagreement as an unresolved refinement issue unless the relevant outcome argument establishes contradiction. Retain the exact effect in either case. Define master axes and how active branches with multiple controls contribute distinct leaves.

For impact, distinguish a direct material influence, a possible transitive consequence, and a parent-contract reconsideration obligation. An influence path is a reason to inspect downstream outcomes, not universal proof that every endpoint will fail under a particular change.

**Acceptance:** test a valid aggregate zero with a changing child outcome, a genuinely contradictory zero, an unallocated parent material effect, and cross-branch shared-state effects. All reports must retain the same distinctions.

### R6 — P1: Define what qualifies a conclusion as supported

**Location:** `docs/language.md:436`, `493–495`, `522–525`, `538–573`.

The spec requires resolved influence evidence for supported assertions, but the evidence contract mainly describes empirical joint success estimation. It does not fully define evidence supporting a zero, a material mechanism, or an assumption marked `validated`. A citation, reason string, or self-assigned status should not automatically establish these claims.

**Recommendation:** separate provenance, influence justification, assumption validation, and probabilistic observations. Define the minimum support accepted by each profile, how support attaches to a specific claim and operating range, and what revisions invalidate it. Permit suitable analytical or contractual arguments without forcing every qualitative influence into binomial trials. The tool can check evidence structure and applicability while clearly leaving substantive review to people or external checkers.

**Acceptance:** adding `because` or changing an assumption's status alone cannot silently promote a conditional result to an established empirical result. Missing, stale, or differently scoped support withdraws only dependent conclusions.

### R7 — P1: Make feasibility an explicit gate for alternative selection

**Location:** `docs/language.md:435`, `445–468`, `533–573`.

Constraints have statements and links, but their assessment and candidate feasibility results are underspecified. Information comparison is meaningful only after checking the common FR set, constraints, acceptance ranges, and enforceable sequencing. A candidate's `dps` list and metadata alone do not demonstrate that gate.

**Recommendation:** define per-candidate feasible, infeasible, and unresolved assessments with reasons. An unknown constraint or uncovered required FR must block a supported Information Axiom recommendation. Preserve the same requirements when comparing alternatives; changing acceptance ranges creates a different design problem. Cost and user priorities should remain explicit decision factors outside information content.

For version 1, accepting documentary feasibility arguments and reporting their evidence limits is enough. General theorem proving is unnecessary.

**Acceptance:** a measured candidate that violates a mandatory constraint cannot outrank a feasible candidate as the preferred AD solution; unresolved feasibility leaves selection provisional.

### R8 — P2: Complete the statistical reporting and selection policy

**Location:** `docs/language.md:538–573`.

Joint empirical trials with Wilson intervals are a defensible initial scope. They are narrower than the skill, which also permits supported analytical probability models. Document that as an intentional version-1 restriction.

**Recommendation:** define positive integral trials, integral failures in `[0,trials]`, confidence strictly between zero and one, the exact Wilson convention, and handling of zero-success/zero-failure samples. Distinguish the boundary point estimate from established certainty, and define infinity in machine-readable output without emitting invalid JSON numbers. Specify whether multiple evidence blocks may be pooled; incompatible exposures or sampling models must not be merged automatically.

Do not turn overlapping confidence intervals into an unsupported winner or claim that marginal intervals alone establish a statistically decisive ranking. A valid outcome is “insufficient evidence to rank.” Include comparative study design in later evidence work if ranking is important.

**Acceptance:** zero trials is invalid; all-success observations retain uncertainty; incompatible horizons cannot be pooled; insufficient comparative evidence keeps a recommendation provisional.

### R9 — P2: Clarify extension authority and outcome status

**Location:** `docs/language.md:293–323`, `386–420`, `650–654`.

Two contracts need sharper boundaries:

1. Generic core `pv.address` is allowed, but duplicating a moved tool-specific address is an error. The spec does not say which owner determines that a core string duplicates an attachment's semantic value, or how that diagnostic preserves core independence.
2. Zero status means the requested operation succeeded, while binding `mismatch`, link `missing`, unknown inputs, and invalid attachments are distinct outcomes. A complete result-to-status table is missing. In particular, successful production of a mismatch report need not mean conformance success.

**Recommendation:** define a role-owned semantic-duplication check at composition, or narrow the forbidden duplication to an explicit field correspondence. Keep core-only analysis usable. Publish a status table separating processing completion, assessment findings, assertion failure, and conformance. Specify treatment of unused required owners for core report operations invoked through a manifest.

**Acceptance:** compare the same model through core-only and manifest inputs, then exercise match, mismatch, unknown, missing behavior target, invalid payload, unavailable owner, and render failure. Core cells stay stable; project completion and conformance remain distinct.

### R10 — P2: Add versioned conformance fixtures and a complete starter project

**Location:** `docs/language.md:193–420`, `621–659`; `examples/`.

The attachment contracts have isolated snippets but no complete manifest-backed project in the current examples. Source reconstructions demonstrate evidence gaps well, while the self-design intentionally leaves major premises unresolved. Neither is a minimal example of a fully supported architecture assessment.

**Recommendation:** add a small synthetic model with proposed, explicitly labeled criteria, one justified triangular mapping, leaf contracts, and both change and failure scenarios. Include a complete project manifest and attachments with deterministic caller-supplied observations and external model revisions. Keep source reconstructions intact as separate fixtures.

Publish expected semantic results and diagnostic categories independently of renderer whitespace and the old Python outputs. Define revision identity: whether formatting/file moves alter source identity, semantic identity, or both; what is hashed; and what invalidates results. Core-only version selection is currently implicitly `/core/1`; specify how future versions will be selected or require a manifest for later versions.

**Acceptance:** the future Go tool can run a documented corpus against versioned expectations. Single-file versus split-file models and input permutations retain semantic conclusions while source locations remain accurate.

## 5. Applying AD to the language/tool architecture

The current rationale identifies author/reviewer needs and maps them to the assessment pipeline. Its reconstructed Python mapping is appropriately unresolved. The revised mapping is a conditional design hypothesis, not an observed architecture result.

For the selected target mechanisms, the rationale's sibling mapping is:

| FR outcome / DP mechanism | Typed admission | Snapshot selection | Binding assessment | Qualified analysis | Reporting |
|---|---|---|---|---|---|
| Preserve admitted facts | X | 0 | 0 | 0 | 0 |
| Trace selected facts | X | X | 0 | 0 | 0 |
| Distinguish drift from missing observations | X | X | X | 0 | 0 |
| Derive qualified conclusions | X | X | X | X | 0 |
| Preserve findings in reports | X | X | X | X | X |

This is conditionally decoupled in the displayed order, assuming the proposed effective diagonals and fixed ownership contracts. The zeros require consumers to preserve upstream facts and policy; they are not justified merely by separating packages. Upstream changes invalidate dependent results. A report change must preserve upstream conclusions. Shared memory, CPU, file access, and failures require separate operating scenarios.

Keep the attachment RFC's local conditional diagonal separate. Binding, behavior-link, and layout controls can be independent within fixed contracts, while core identity changes and composed findings still affect the whole assessment. No global uncoupled conclusion follows.

Recommended refinement of responsibilities:

| Responsibility | Owned contract | Failure result / useful acceptance case |
|---|---|---|
| Syntax admission | Native syntax plus the explicit expression whitelist | Positioned rejection of unsupported expressions, including hidden templates |
| Typed resolution | R1 schema, typed identities, hierarchy | Wrong-kind reference cannot enter dependent analysis |
| Snapshot selection | R2 activation and R3 applicability | Candidate switch preserves alternatives and removes inactive facts from conclusions |
| Influence analysis | R3–R6 resolved cells, pairing, order, refinement | Ambiguous pairing stays unresolved; known justified cycles remain visible |
| Candidate assessment | R7 feasibility and R8 comparable evidence | No ranking across different required outcomes or unsupported trials |
| Extension composition | R9 authority, revisions, partial results | Invalid attachment cannot erase independent core findings |
| Reporting | One qualified assessment and explicit operation status | All views retain unknowns, conflicts, premises, and failure status |

These are logical responsibilities; they need not become separate processes or a fixed Go package layout. C junctions describe required design sequencing, with runtime order derived from actual contracts. S combines independent results. Any F behavior must retain convergence, stopping, and failure obligations.

There is no basis for a numerical information score for this architecture. Go and native HCL are fixed user/project choices. Compare implementation alternatives later against the same corpus and success predicates; record cost and complexity separately from probability.

## 6. Go implementation sequence and validation

Resolve R1–R7 as normative text and fixtures before implementing analysis that callers will trust. Then implement the smallest useful core path: native parse → profile admission → typed graph → snapshot → qualified cells/classification → reports. The adopted extension contracts remain part of the planned project feature set; staging implementation does not remove their requirements.

Use native AST inspection before evaluating accepted literal forms. HCL exposes expression nodes and source ranges; parsing or literal evaluation alone does not enforce the restricted profile. Inspect object entries before materializing maps so duplicate keys cannot disappear. Preserve typed traversals rather than converting references to ambiguous strings. These are implementation suggestions grounded in HCL's APIs, not new authored language syntax. [H4]

Useful conformance cases, beyond the individual recommendations:

- Reject interpolation in strings/heredocs, calls, indexing, arithmetic, and computed object keys; accept documented literal escapes, negative numbers, and native numeric notation.
- Exercise file identity, symlink containment, duplicate references to the same input, and wrong input suffixes under the existing manifest contract.
- Verify that all reports share one resolved assessment, with traceable sources and deterministic semantic results.
- Run DP-change scenarios that inspect affected FR predicates, including shared-state and failure cases; do not use unchanged files as evidence of independence.
- Verify that a source-profile pass never implies architecture completeness, implementation conformance, or supported independence.

## 7. Can the language become uncoupled?

A conditional diagonal design is possible for changes within the attachment contracts.
The current evidence does not support a diagonal design for the whole language.
This section proposes a way to establish the narrower claim.
It does not replace the five outcomes in Section 5.

Uncoupled means that each design parameter affects only its paired functional requirement.
Decoupled means that the design requires a sequence of choices.
Both terms apply to a defined mapping and range of changes.
A file extension alone has neither property.

### 7.1. The limit of the current mapping

The existing needs remain in scope.
They cover faithful design records, safe input, traceable changes, exchange with other tools, and readable reports.
Go, native HCL, and separate behavior models remain fixed choices.

Section 5 records a conditional triangular mapping for these needs.
Its claims include the following part:

| Outcome / control | DP1: Typed admission | DP4: Reporting |
|---|---|---|
| FR1: Preserve admitted facts | X | 0 |
| FR4: Preserve findings in reports | X | X |

The proposed DP1 mechanism controls which facts survive admission.
The rationale claims that lost facts can prevent reports from preserving the required findings.
DP4 controls the presentation of those findings.
Its read access cannot change the admitted facts under the stated ownership contract.

If this influence model holds, reordering its rows and columns cannot remove its extra `X`.
Separate files, packages, interfaces, or processes also cannot establish that zero.
A new mechanism must remove the material effect on FR4.

A changed input or report value alone does not prove a material effect.
The relevant question is whether the change affects an FR's acceptance criterion.
The future acceptance work must test the rationale's claimed effects on those criteria.
This review does not prove that every possible redesign must retain this matrix.

Freezing DP1 removes its changes from the analysis range.
That permits a narrower analysis, but it does not establish independence when DP1 changes.
Combining every outcome into one FR also hides the original independence question.
This proposal uses neither step to claim whole-language independence.

### 7.2. Proposed scope and traceability

The accepted RFC already proposes independent attachment owners.
This proposal gives that design explicit acceptance work.
It does not introduce a competing extension architecture.

A core snapshot is one selected design with fixed facts.
An owner contract defines an extension's inputs and permitted results.
A payload is the data supplied to that owner.
The proposed range permits payload changes within fixed owner contracts and one core snapshot.

The parent outcome, FR-E, is to extend a design assessment without changing core meaning or another extension's result rules.
It serves N1, N3, N4, and N5 from the rationale.
N2 also applies because owners must reject invalid payloads.
These are proposed acceptance criteria, not measured results.

DP-E is the selected mechanism: typed attachments with separate input ownership and a common result contract.
After selecting DP-E, its child requirements and controls are:

| Child FR / needs | Proposed acceptance criterion | Paired DP |
|---|---|---|
| FR-E1 / N2,N3,N4: Assess a realization binding | Available observations produce the specified match or mismatch. Missing observations produce unknown with a cause. | DP-E1: A binding owner with its own payload decoder and comparison rules |
| FR-E2 / N2,N4: Resolve a behavior target | The owner resolves the exact revision and target. Missing targets and unavailable revisions retain their distinct results. | DP-E2: A behavior owner with its own payload decoder and target resolution rules |
| FR-E3 / N1,N2,N5: Present every qualified finding | Either supported layout preserves every finding, qualification, and required source location. | DP-E3: A view owner that renders the complete result contract |

The core requirements remain at the parent level and in Section 5.
They do not disappear into constraints.
The fixed snapshot defines the range for this child analysis only.

### 7.3. Proposed diagonal matrix

The following matrix is a conditional design hypothesis.
`X` marks an intended material control.
`0` marks an absence of material influence under the contracts explained below.
Without evidence for those contracts, supported classification remains unresolved.

| Outcome / control | DP-E1: Binding owner | DP-E2: Behavior owner | DP-E3: View owner |
|---|---|---|---|
| FR-E1: Assess a binding | X | 0 | 0 |
| FR-E2: Resolve a target | 0 | X | 0 |
| FR-E3: Preserve findings in either layout | 0 | 0 | X |

Each diagonal has a distinct control.
The binding comparison determines FR-E1.
The target resolution rules determine FR-E2.
The rendering rules determine FR-E3.
None of these controls comes only from a component name.

The four zeros in the first two rows require separate ownership.
The behavior and view owners cannot change binding inputs, observations, or comparison rules.
The binding and view owners cannot change behavior inputs, external revisions, or target resolution rules.
They also cannot replace another owner's result.

The remaining two zeros concern presentation fidelity.
The view owner must render every result permitted by the fixed result contract.
A binding mismatch or missing behavior target changes report content.
It does not prevent faithful presentation when the renderer handles that valid result.
If a permitted result breaks presentation, the corresponding zero fails.

FR-E3 differs from the broader FR4 in Section 5.
It covers layout fidelity within a fixed result contract.
It does not establish that all changes to admitted facts preserve complete reports.
The local diagonal therefore leaves the parent mapping unchanged.

### 7.4. Responsibilities and failure behavior

The Go tool can implement these logical boundaries within one program.
Separate processes are not required by functional independence.
The mechanism requires authority limits and complete contracts, not a particular deployment layout.

The required responsibilities are:

| Responsibility | Inputs and outputs | Owned information | Failure behavior |
|---|---|---|---|
| Attachment loader | Manifest, core snapshot, and attachments to typed owner inputs | Subject identity, owner identity, and source locations | Reject invalid envelopes before owner execution. Preserve independent core findings. |
| Binding owner | Its payload and observations to a binding result | Payload meaning and comparison rules | Return unknown for unavailable observations. Report invalid payloads as errors. |
| Behavior owner | Its payload and external revision to a link result | Payload meaning and target resolution rules | Distinguish a missing target from an unavailable revision. |
| Result composer | Core findings and owner results to one qualified assessment | Result identity and completeness status | Retain completed results. Reject stale results and conflicting identities. |
| View owner | Qualified assessment and layout payload to a report | Layout rules | Preserve every finding. Report a rendering failure without changing completed analysis results. |

The loader must give each owner only its own payloads and permitted core data.
The composer must retain the input revisions for each result.
If an input changes, it must reject stale dependent results.
It must also keep processing failure separate from an adverse design finding.

An S junction combines independently established child outcomes.
It does not require concurrent execution.
The loader, composer, and renderer still require runtime order.
That order alone does not make the child matrix triangular.
No F junction is proposed because these owners do not require iterative correction of each other's controls.

### 7.5. Work needed to support the zeros

The future implementation must exercise each control while holding the other controls fixed.
The trials must compare outcome criteria, not only changed files or result bytes.
They must cover valid adverse results as well as successful results.

The required scenarios are:

| Scenario | Required result |
|---|---|
| Change only a valid binding payload | FR-E1 follows the new binding. FR-E2 remains satisfied. Both layouts preserve the new findings. |
| Change only a valid behavior target | FR-E2 follows the new target. FR-E1 remains satisfied. Both layouts preserve the new findings. |
| Change only the supported layout | FR-E3 remains satisfied. Core findings and both other owner results remain identical. |
| Supply invalid data to one owner | That owner reports the error. Other completed owner results remain intact. The project reports incomplete processing. |
| Remove observations or an external revision | The affected result becomes unknown. Both layouts preserve its cause and qualification. |
| Change the core schema or result contract | The tool requires renewed assessment. It does not reuse the local diagonal as support. |
| Add an unforeseen result case | The view must handle it under an updated contract. Existing evidence does not cover that contract change. |
| Exhaust shared memory or interrupt file access | The assessment retains an operational evidence gap. The local semantic matrix does not establish failure isolation. |

The first five scenarios test the proposed range.
The last three expose its limits.
No execution results exist for these scenarios.

Shared resources can affect several outcomes at once.
The current specification supplies no resource bounds or recovery targets for this proposal.
Those effects remain `?` in an operational analysis.
A future availability requirement needs its own criteria, controls, and cross-branch analysis.

### 7.6. Alternatives and decision

The alternatives must preserve the same child outcomes and acceptance criteria.
Separate ownership must establish real limits on effects.
The number of files or modules does not decide independence.

### 7.7. Before and after in HCL

The examples below make the local proposal concrete.
They use the accepted attachment syntax from `docs/language.md`.
No new keyword can remove a material influence from the whole design.

The proposed change is to place each extension's data under its own owner.
The owner must also control its interpretation and result rules.
The future Go tool must enforce those limits before the local diagonal has support.

These fragments are illustrative and do not form a complete model.
They assume that `design.catalog`, `dp.catalog_store`, and `dp.catalog_query` exist in the core model.
The declarations below supply the referenced PV and module.
The model still needs its needs, FRs, criteria, influences, and module contracts.

#### 7.7.1. Move a tool-specific address to its binding owner

The current core syntax permits a descriptive `pv.address`.
That field alone does not select a comparison rule or supply observations.
The proposed layout moves the tool-specific value into a binding attachment.

Before:

```hcl
# process.ad.hcl
pv "catalog_database" {
  realizes = [dp.catalog_store]
  kind = "infrastructure"
  address = "aws_db_instance.catalog"
}
```

After:

```hcl
# process.ad.hcl
pv "catalog_database" {
  realizes = [dp.catalog_store]
  kind = "infrastructure"
}

# bindings.ad.ext.hcl
attachment "catalog_storage" {
  owner = extension.terraform_binding
  subject = pv.catalog_database
  data = {
    address = "aws_db_instance.catalog"
    observation_source = "terraform_state"
  }
}
```

The binding owner interprets the address and compares caller-supplied observations.
The core PV keeps its realization link.
The moved address must not remain in both places.

This change supplies an authority boundary for DP-E1.
It does not prove that binding changes leave every parent outcome unaffected.
Missing observations still produce unknown, and a match still does not prove FR satisfaction.

#### 7.7.2. Give behavior links a separate owner

The current core module syntax records realization responsibilities.
It does not resolve an external behavior target by itself.
The proposal adds that responsibility through the behavior owner.

Before:

```hcl
# process.ad.hcl
module "catalog_search" {
  realizes = [dp.catalog_query]
}
```

After:

```hcl
# process.ad.hcl
module "catalog_search" {
  realizes = [dp.catalog_query]
}

# behavior.ad.ext.hcl
attachment "catalog_search_behavior" {
  owner = extension.event_model_link
  subject = module.catalog_search
  data = {
    model = "library_behavior"
    revision = "library-behavior-r17"
    target_kind = "slice"
    target_label = "search_catalog"
  }
}
```

The behavior owner resolves the exact external revision and target.
It cannot change the binding payload or comparison rules.
The binding owner cannot change this target or its resolution rules.

These limits defend the zeros between FR-E1 and DP-E2, and between FR-E2 and DP-E1.
An unavailable revision produces unknown.
A missing target in an available revision produces missing.

#### 7.7.3. Declare the separate owners in a manifest

A manifest lists a project's files and extension owners.
A core-only model does not load owners or discover attachments.
The proposal adds a manifest when the project needs extension results.

Before:

```hcl
# No .ad.project.hcl manifest exists.
# The core input includes these files:
# design.ad.hcl
# process.ad.hcl
# No attachment owner runs for a core-only input.
```

After:

```hcl
# catalog.ad.project.hcl
project "catalog" {
  language = "requirements_hcl/core/1"
  core_files = [
    "design.ad.hcl",
    "process.ad.hcl",
  ]
  attachment_files = [
    "bindings.ad.ext.hcl",
    "behavior.ad.ext.hcl",
    "views.ad.ext.hcl",
  ]
}

extension "terraform_binding" {
  role = "binding"
  contract = "requirements_hcl/terraform_binding/1"
}

extension "event_model_link" {
  role = "behavior_link"
  contract = "requirements_hcl/event_model_link/1"
}

extension "html_view" {
  role = "view"
  contract = "requirements_hcl/html_view/1"
}
```

The extension labels select trusted installed owners.
The manifest does not install those owners or download external models.
Each attachment file contains only its attachment blocks.

The manifest supplies input selection and owner contracts.
It does not establish independence through file separation.
The loader and owners must enforce the authority limits in Section 7.4.

#### 7.7.4. Change layout without changing assessment rules

The current contract permits two layouts.
Both layouts must preserve every finding and qualification.
The following change exercises DP-E3 while the core, binding, and behavior inputs stay fixed.

Before:

```hcl
# views.ad.ext.hcl
attachment "review_layout" {
  owner = extension.html_view
  subject = design.catalog
  data = {
    layout = "requirements_first"
    show_source_locations = true
  }
}
```

After:

```hcl
# views.ad.ext.hcl
attachment "review_layout" {
  owner = extension.html_view
  subject = design.catalog
  data = {
    layout = "matrices_first"
    show_source_locations = true
  }
}
```

The report order changes.
The binding result, behavior result, core findings, and assessment status must remain identical.
A rendering failure still causes the requested rendering operation to fail.

Conversely, a changed binding or behavior result must appear in either layout.
The view's acceptance criterion concerns faithful presentation, not identical report content.
That distinction supports the proposed zeros from DP-E1 and DP-E2 to FR-E3 within the fixed result contract.

#### 7.7.5. Keep whole-language assertions honest

The current self-design describes a conditional decoupled pipeline.
Its material effects do not disappear after attachment migration.
A matching assertion can retain that claim for its original scope:

```hcl
# A fragment of the self-design model.
expect "assessment_pipeline" {
  scope = dp.assessment_pipeline
  classification = "decoupled"
  basis = "conditional"
  under = context.semantic_changes

    dp.checked_graph,
    dp.candidate_snapshot,
    dp.binding_assessment,
    dp.qualified_analysis,
    dp.read_only_reports,
  ]
}
```

This fragment illustrates the retained pipeline claim.
It is not a new observation or a complete self-design fixture.
Changing `classification` to `uncoupled` cannot supply missing zeros or remove known effects.

The extension subtree needs its own FRs, DPs, influences, premises, and scope before an `expect` block can test its proposed diagonal.
An `expect` block can test that analysis result.
It cannot create the result by assertion.

The proposed syntax layout can support a conditional diagonal for the three extension outcomes.
It does not establish a diagonal for the whole `.ad.hcl` language.
The Go implementation and the acceptance work in Section 7.5 remain necessary.

That result covers syntax only.
It does not establish complete models, resolved references, enforced owner boundaries, or supported independence.
